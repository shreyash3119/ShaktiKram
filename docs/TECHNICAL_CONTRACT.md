# Technical Contract (Backend Stage 0)

Status: **Draft for review.** No Stage 1 code starts until this is approved by all three contributors.
Changes to this file need a pull request reviewed by all three.

Sources: Complete Development Plan (newer, wins on conflicts), Architecture v2, Feature Specification.
Conflict resolutions are in `DECISIONS.md`.

---

## 1. Principles

1. One PostgreSQL database is the single source of truth.
2. Three kinds of information, stored differently:
   - **Plans** (templates, splits, prescriptions, supplement phases, targets): versioned, never edited in place.
   - **Facts** (sets, measurements, doses, check-ins, pain entries): recorded entries. Corrections go through audit.
   - **Insights** (suggestions, readiness, PR flags, summaries): derived, rebuildable, never typed in by hand.
3. History is never overwritten or silently lost.
4. Manual muscle-development ratings are the user's own assessment. They are never calculated from weight, reps, sets or volume.
5. The app gives observations and suggestions. It never diagnoses or gives medical advice.
6. One implementation of each business rule per layer (see section 11).

JSON keys are `snake_case` and match column names.

## 3. Identity and common columns

There is **no `user_id`** and no users table (single user, decision D4).

Every client-writable table has:

| Column | Type | Rule |
| --- | --- | --- |
| `id` | uuid | UUIDv7, generated by the client so offline creation never clashes. The database provides a `uuid_v7()` function as a fallback default. |
| `created_at` | timestamptz | Set on insert. |
| `updated_at` | timestamptz | Set by trigger on every update. |
| `deleted_at` | timestamptz null | Soft delete. Null means alive. |
| `rev` | bigint | Assigned by trigger from one global sequence on every insert, update and soft delete. Never client-supplied. |
| `device_id` | uuid | Device that last wrote the row. Set by the database from the transaction's `pfs.device_id`, which only the API functions set. |

**Event tables** (things that happened) also have `occurred_at timestamptz`, `local_date date`, `tz_offset_minutes smallint`.
`local_date` must equal the calendar date of `occurred_at` shifted by `tz_offset_minutes`; the database rejects a mismatch.
Streaks, attendance and daily reports use `local_date`.

**Restore mode.** Triggers normally assign `rev`, `updated_at` and `device_id` and write audit rows. For a logical restore, a server-side role sets `pfs.restore_mode = 'on'`: values are kept as supplied and no audit rows are written. The mode is ignored for the `anon` and `authenticated` roles and the API switches it off. After loading, `pfs_restore_finish()` moves the revision sequence past the highest restored `rev` and logs a `restore` audit row.

**Reference tables** (`muscles`, `body_regions`, `equipment`) have a stable `key` (unique, from `shared/vocabulary/`) and an `is_custom` flag. Seeded rows are never deleted; custom rows follow the common-column rules.

## 4. Vocabulary and enumerated values

- The single source is `shared/vocabulary/*.json`. No private copies in Dart, Python or SQL.
- Large or extensible lists (muscles, body regions) become reference tables seeded from the JSON.
- Closed lists (statuses, scales, types) become `text` columns with a `CHECK` constraint generated from the JSON.
- A test asserts that migrations, seed data and the JSON agree. A mismatch fails the build.
- Adding a value is a vocabulary change: edit the JSON, add a migration, update tests.

## 5. Units, dates and time

| Quantity | Stored as | Type |
| --- | --- | --- |
| Weight, mass | kilograms | `numeric(6,2)` |
| Body measurements | centimetres | `numeric(5,1)` |
| Distance | metres | `numeric(9,1)` |
| Duration | seconds | `integer` |
| Water | millilitres | `integer` |
| Nutrition | grams and kcal | `numeric(7,1)` |
| Speed | metres per second | `numeric(5,2)` |
| Heart rate | beats per minute | `smallint` |

- Conversion (lb, miles, etc.) happens only for display. The user's display units live in `settings`.
- All timestamps are stored and transmitted in UTC (ISO 8601 with `Z`).
- The user's IANA time zone is stored in `settings`; each event also stores its own `tz_offset_minutes`.
- Dates are `YYYY-MM-DD` in JSON.
- Derived values (fat mass, lean mass) are calculated in views, not stored.

## 6. Versioning of plans

Applies to: template versions, split versions, profile versions, supplement phases, muscle priorities, nutrition targets.

Columns on a versioned table: `entity_id` (stable identity), `version` (1, 2, 3...), `effective_from`, `effective_to` (null = current), `previous_version_id`, `change_reason`.

Rules:
1. Editing never updates a versioned row. It calls one function that closes the current version (`effective_to = new effective_from`) and inserts the next.
2. `effective_from` is `timestamptz` and the interval is half-open `[from, to)`.
3. A new version may not start before the current one. The database enforces this with a trigger and an exclusion constraint (no overlapping intervals per entity). Violation returns `version_conflict`.
4. Version rows are immutable except for closing `effective_to`.
5. Sessions store the version ids that applied (`split_version_id`, `template_version_id`). Each session exercise also stores a `prescription_snapshot` as a second safeguard.

## 7. Audit and corrections

- `audit_log` columns: `id`, `table_name`, `record_id`, `action` (`insert`, `update`, `delete`, `version_close`, `restore`), `before` (jsonb), `after` (jsonb), `reason` (text, optional), `device_id`, `at`, `rev`.
- Written by database triggers on every update, soft delete and version close of registered tables. Inserts are logged for plan and goal tables only, to keep the log small. An update stores only the changed columns (`before` and `after`). `device_id` and `reason` come from the API transaction (`reason` is the optional `reason` field of an operation).
- `audit_log` is append-only. Updates and deletes are blocked.
- Hard deletes are blocked on all tables except through the restore and purge functions (Stage 5).
- A correction to a fact (for example, fixing a set's weight) is an ordinary update. The old values go to `audit_log`. Derived records such as personal records keep history even if the supporting set is later corrected.

## 8. Private access and security

Decision D3: one owner account in Supabase Auth. There is no registration screen and no multi-user model.

1. **One owner.** Sign-ups are disabled in Supabase Auth. The owner account is created once by hand. The first signed-in user to call `api_claim_owner()` becomes the owner (stored in `app_owner`); after that nobody else can claim it. `is_owner()` checks `auth.uid()` against `app_owner`.
2. **Sign in once per device.** Each device signs in once (email and password). The session persists through refresh-token rotation, so there is no daily login. Access tokens last one hour.
3. **Row Level Security** is enabled on every table (`pfs_attach` and `pfs_secure` do it automatically, and a test fails the build if a table lacks it). The `anon` role has no access. The `authenticated` role can read only while `is_owner()` is true, and has no insert, update or delete grants. Reads use Supabase REST (PostgREST) under these policies.
4. **Writes only through the API functions** (`api_apply_operations` and the device functions, section 9). Internal `pfs_*` functions are not executable by clients.
5. **Devices.** Each device registers once (`api_register_device`) and sends its `device_id` with every write and pull. `api_revoke_device` blocks that device's writes and pulls at once. Its REST reads continue until its access token expires, because RLS cannot tell devices apart; for a lost device also sign out all sessions and change the password.
6. **Clients never hold the service-role key or the database password.** Secrets live in server environment variables and are never committed.
7. **Storage buckets** (`media`, `backups`) are private. Only the owner can use them; files are reached through short-lived signed URLs. `backups` is read-only for the owner.
8. **Web client:** on hold (D2). It will use the same owner sign-in.

## 9. API surface and conventions

Supabase and FastAPI interaction:

| Concern | Where it lives |
| --- | --- |
| Table reads, simple filtered lists, views | Supabase auto-generated REST (PostgREST), read-only, under RLS |
| All writes (create, edit, delete, new version) | One function: `api_apply_operations` (section 10). Used by phone sync and by web edits alike |
| Business rules that guard writes (version overlap, restrictions) | Database triggers and functions |
| Reports, Excel, PDF, backup export | FastAPI, only when Stage 5 needs Python |
| FastAPI to database | Uses a server-only database role. Calls the same SQL functions. It does not re-implement write rules |

### Stage 1 functions (full reference: `shared/api_contracts/stage1_functions.md`)

`api_claim_owner`, `api_register_device`, `api_list_devices`, `api_revoke_device`, `api_apply_operations`, `api_pull_changes`.

### Request conventions
- JSON body, `Content-Type: application/json`.
- Every write request includes `device_id` and a client `request_id` (uuid).
- List requests use keyset pagination: `limit` (default 50, max 500) and `cursor`.
- Filters use plain field names: `from_date`, `to_date`, `exercise_id`, `status`.

### Success response
```json
{
  "data": {},
  "meta": {
    "request_id": "uuid",
    "server_time": "2026-11-05T03:40:00Z",
    "schema_version": 1,
    "next_cursor": null
  }
}
```

### Error response
```json
{
  "error": {
    "code": "validation_failed",
    "message": "Human-readable summary",
    "details": [{ "field": "reps", "issue": "must be greater than 0" }],
    "request_id": "uuid"
  }
}
```

Codes and HTTP statuses are listed in `shared/api_contracts/error_codes.json`.
Clients branch on `code`, never on `message`.

Insight payloads label every value with `kind`: `measured`, `estimated` or `suggestion`, and carry a plain-language `reasoning` field.

## 10. Operations and sync

One write interface for both clients. A request carries an ordered list of **operations**:

```json
{
  "device_id": "uuid",
  "operations": [
    {
      "op_id": "uuid",
      "seq": 41,
      "entity": "sets",
      "action": "upsert",
      "record_id": "uuid",
      "base_rev": 1203,
      "client_updated_at": "2026-11-05T03:35:00Z",
      "reason": "optional text for the audit log",
      "payload": {}
    }
  ]
}
```

Actions: `upsert`, `delete` (soft), `new_version` (versioned plan tables only).

Rules:
1. **Idempotency.** `op_id` is recorded in `sync_operations`. Replaying an already-applied `op_id` returns the original result and changes nothing.
2. **Ordering.** Operations from one device are applied in `seq` order. Each runs in its own savepoint so one failure does not roll back the others. The whole request takes one database-wide write lock, so writes are serialised (single user). The response lists a result per operation: `applied`, `duplicate`, `rejected` (with error code) or `conflict`.
3. **Revisions.** Every change gets the next global `rev`. Pull: `since_rev`, `limit` returns changed rows (including soft-deleted ones) in `rev` order, plus `next_rev` and `has_more`. Because writes are serialised, committed revisions are always a contiguous prefix and a pull cannot skip a row.
4. **Conflict policy by record class:**
   - *Append-only facts* (sets, supplement doses, check-ins, water logs, pain entries): a create for an existing id is ignored (`duplicate`). A correction must send `base_rev` equal to the current `rev`; it is then applied and audited.
   - *Ordinary editable records*: an edit must send `base_rev` (without it the operation is treated as a re-sent create and ignored). A conflict exists only if `base_rev` is older than the stored `rev` **and a different device wrote the row**. A device's own earlier edits never conflict. On a conflict the later `client_updated_at` wins (the loser gets result `conflict` and the server copy stays). `client_updated_at` is clamped to server time plus 5 minutes. Overwritten values stay in `audit_log`.
   - *Versioned plans*: the server refuses a version that would start before the current one (`version_conflict`). The client asks the user to review.
5. **Deletes** are soft and propagate through pull as rows with `deleted_at` set.
6. **Media.** Files are uploaded to private storage first (hash-named, resumable). Then an operation creates the `media_assets` row. A failed upload leaves no row.
7. **Web client** is on hold (D2). If it edits later, it uses the same operations, sent one at a time.

## 11. Calculations

1. Each rule (progression, estimated 1RM, PR detection, readiness, consistency, exposure) is written once as a plain-language spec in `shared/calculation_specs/`, with example inputs and outputs in `shared/test_vectors/`.
2. The server has exactly one implementation per rule, recorded in a registry in the spec. Simple aggregates are SQL views. Complex rules are Python in FastAPI. Never both for one rule.
3. The phone implements in Dart only what it needs offline (next-set suggestion, PR detection, readiness). Server and Dart both pass the same test vectors.
4. Results are cached in `insight_cache` with an `inputs_hash`, and can be rebuilt at any time.

## 12. Wording and safety rules

- Use "observation" and "suggestion". Never "diagnosis", "treatment" or "you should take/stop".
- Supplement tracking records what the user entered. The app never tells the user to start, stop or change a supplement.
- A pain, injury or readiness result that looks concerning prompts review of the symptoms, not an automated training decision.
- Muscle rating changes are described as "a change in your assessment", never as proof of growth.
- Planned breaks and rest days are never counted as missed workouts.

## 13. Environments, migrations and seeds

- Environments: local (Supabase CLI), `dev` project, later `prod`.
- Migrations are forward-only. An applied migration is never edited; add a new one.
- Reference seed data (muscles, body regions, vocabulary rows) is applied by migration and is idempotent.
- `seed.sql` holds fictional development data only, and is never run in production.
- Every migration has at least one test in `backend/tests/`. `backend/tests/run.sh` builds a scratch database from all migrations and runs every test, including a backup and restore round trip.

## 14. Definition of done for a module

A module is done when it has: migrations, constraints and indexes; RLS; operations through `api_apply_operations`; read views; tests (including history preservation and audit); API contract entries in `shared/api_contracts/`; seed examples; and a reviewed pull request from a second contributor.

## 15. Stage 2 conventions

- **Plans with children.** A template or split is an identity row plus immutable versions. The child rows of a version (`template_exercises`, `split_days`, `split_day_muscles`) may change only while their version is open and unused. After a session or schedule entry uses it, or after it is closed, the database refuses changes (`immutable_record`) and the client creates a new version and new child rows.
- **Creating a version through the API.** Send a `new_version` operation. Put the id the client wants for the new version row in `payload.id`, and send child rows in later operations of the same request (operations run in `seq` order).
- **Session snapshots.** A session exercise created from a template row gets a copy of its prescription (`prescription_snapshot`). The snapshot never changes afterwards.
- **Views** use `security_invoker`, so row level security applies to the caller. Grant select on a new view explicitly.
- **Functions** are closed by default. A new function a client needs must be granted `execute` in its migration.
- **Weeks** in attendance and volume views start on Monday.

## 16. Stage 3 conventions

- **Labelled values.** A view that calculates something says what it is: `value_kind` is `estimated` (body composition, nutrition) or `user_assessment` (muscle ratings). Nothing calculated is called `measured`.
- **Observation flags.** `suggest_professional_review`, `exceeds_recorded_limit` and restriction warnings describe what the user recorded. They never diagnose, prescribe, or tell the user to start, stop or change anything.
- **Ratings versus exposure.** Muscle ratings come only from assessments the user entered. Training exposure (sets, frequency, effort) is a separate view and is shown beside a rating, never merged into it.
- **Versioned targets and phases.** `personal_targets`, `supplement_phases` and `muscle_priorities` are versioned. A day is compared with the version that applied on that local day.
- **Reminder rules.** `schedule` is `{}` or `{"type":"daily|weekly|once","time":"HH:MM","days":[1..7],"date":"YYYY-MM-DD"}`. The database rejects any other shape. `api_due_reminders` answers what fires in a window; the device delivers it.
- **Weeks** in the new weekly views start on Monday, like Stage 2.

## 17. Stage 4 conventions

- **One implementation per rule.** A rule is a plain-language spec, a SQL `calc_*` function (one JSON object in, one out) and shared test cases. The phone implements only what it needs offline and must pass the same cases.
- **Results say what they are.** `value_kind` is `suggestion`, `observation` or `estimated`. Suggestions carry `reason_codes` (for machines) and `reasoning` (for people). Nothing is applied automatically.
- **Written by the database.** `personal_records` and `achievements` are filled by deferred triggers at commit and are read-only for clients. Re-running detection is safe.
- **Internal functions stay closed.** `pfs_*` and `calc_*` functions are not granted to clients; only `api_*` functions are, and each checks the owner.
- **Views that call functions.** A `security_invoker` view runs its functions as the caller, so the functions it needs are granted explicitly.

## 18. Stage 5 conventions

- **The reporting service only reads.** It connects as `pfs_reader` (read everything, write nothing). Every write still goes through `api_apply_operations`. A migration that adds a view ends with `select pfs_grant_reader();`.
- **Who may call it.** The app sends the owner's Supabase access token. The service asks Supabase Auth who it is and checks the user against `app_owner`. No token gives 401, another account 403.
- **Report figures come from the views**, so the app and the reports agree. Estimates (`estimated`) and the user's own ratings (`user_assessment`) stay labelled in every export. Observations are cautious statements taken from the figures, never advice or a diagnosis.
- **Backups.** One zip with `manifest.json` and `data.json`. Each table is the exact JSON text PostgreSQL produces, taken in one consistent snapshot in UTC, with a row count and a content hash per table (`pfs_table_fingerprints()`), a hash of the data file and a hash of the database layout.
- **Restore is a command-line operation** (`backend/scripts/restore_backup.py`). It needs a role that can write and a clean, freshly migrated database. Foreign keys are checked and every table's row count and content hash must match before anything is kept.
- **A CSV export is not a backup.** It is for reading in a spreadsheet and cannot be restored.
